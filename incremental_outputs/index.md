# AIコーディング時代のインクリメンタル開発
## 振る舞い検証ファーストという新しい品質保証のあり方

---

## 1. イントロ：レトロスペクティブでの違和感

### 1.1 「インクリメントが出ない」という声
- スプリントレビュー後のレトロで出た課題
- 一見シンプルな要望だが、議論が噛み合わなかった
- なぜ伝わらなかったのか？その背景にある本質的な問題

### 1.2 この記事で伝えたいこと
- AIコーディング時代に必要な、品質保証の考え方の転換
- 「インクリメント」という言葉が持つ多層性
- 実践的な解決の方向性

---

## 2. 「インクリメント」の3つの層

### 2.1 層の整理
**PO視点：スプリントインクリメント**
- PBIの完成、POへのデモ可能な状態
- スクラム的な「完成の定義」
- サイクル：1-2週間

**タスクマネジメント視点：タスクインクリメント**
- 個々のタスクの完了
- PR作成、マージ可能な状態
- サイクル：数時間〜1日

**開発者視点：バイブコーディングインクリメント**
- AIとの対話における最小の進捗単位
- 「ちょっと書いて、すぐ確認」の繰り返し
- サイクル：数分〜30分

### 2.2 なぜ「どこから手をつけるか」が問いになるのか
- 3つの層は独立していない、密着している
- でも、認識が揃っていないと空中戦になる
- メンバーそれぞれが違う層の話をしていた可能性

---

## 3. より深い問題：品質保証の方法論が変わっていない

### 3.1 従来の開発フロー
```
コードを書く
↓
ソースコードレビュー（★ここで品質を担保）
↓
動かしてみる
↓
PR通す
```

### 3.2 AIコーディングでこのフローが破綻する理由
- AIが大量のコードを生成する時代
- 人間が全行レビューすることの限界
- でも「ちゃんと読まなきゃ」という責任感のプレッシャー
- 結果：PRが通らない、インクリメントが出ない

### 3.3 「コードレビュー = 品質保証」という前提への疑問
- 開発者の責務は「理解すること」と「保証すること」は別
- ソースコードレベルでの完璧性を求めすぎていないか
- 保証すべき品質とは何か？

---

## 4. 提案：振る舞い検証ファーストへの転換

### 4.1 検証の3つの層
**第1層：振る舞いの検証（最優先）**
- ユーザーストーリー、受け入れ基準
- E2Eテスト、統合テスト
- 「何ができるようになったか」の検証

**第2層：テストコードの検証（中優先）**
- ユニットテストの妥当性
- カバレッジ、テストの保守性

**第3層：ソースコードの検証（最低限）**
- セキュリティ、パフォーマンスの重大な問題
- 明らかなアンチパターン
- リスクベースの限定的なレビュー

### 4.2 なぜ振る舞い検証が最優先か
**AIの出力の不確実性への対応**
- 実装は毎回変わりうる
- 振る舞いが正しければ、実装の揺れは許容

**インクリメンタル開発との相性**
- 各イテレーションで「何ができたか」が明確
- 価値の早期提供

**リファクタリングの安全性**
- 振る舞いテストがあれば実装変更を恐れない

### 4.3 開発者の責務の再定義
```
開発者がすべきこと:
✓ システムの振る舞いを設計・検証
✓ アーキテクチャの方向性を決定
✓ AIに適切な指示を出せるよう構造を理解
✓ 重要な判断ポイント（セキュリティ等）を見極め

開発者がしなくていいこと:
✗ すべての実装詳細を行単位で検証
✗ AIが書いたコードの最適性を完全に保証
✗ 「自分が書いたかのように」全てを把握
```

## 5. 実践編：3つの層すべてで振る舞い検証ファーストを実現する

### 5.1 バイブコーディングレベル
```
1. AIにコード生成させる
2. すぐ実行して期待通りか確認（数分）
3. 動いたら次へ
```
これが最小のインクリメント

### 5.2 タスクレベル
```
1. タスクの受け入れ条件を明確にする
2. 振る舞いテストを書く（または手動確認手順）
3. AIでコード生成
4. 動作確認できたらPR
5. ソースコードレビューは最低限（完璧を待たない）
```

### 5.3 PBIレベル
```
1. 受け入れ基準をPOと合意
2. デモシナリオを準備
3. E2Eテストで自動化（可能なら）
4. POにデモ
```

### 5.4 具体的なワークフロー例
**従来**
- タスクを取る → コードを書く → レビュー待ち → 修正 → （数日後）マージ

**提案**
- タスクを取る → 期待動作を定義（5分） → AIにコード生成（15分） → 動作確認 → 即PR → （数時間後）マージ

## 6. よくある懸念への回答

### Q1: ソースコードレビューを軽視すると品質が下がるのでは？
A: 品質保証の手段を「動的」にシフトする。テスト、モニタリング、カナリアリリースで担保。

### Q2: AIが生成したコードを理解せずにマージして大丈夫？
A: 理解のレベルを適切に。重要な部分は詳細に、そうでない部分は振る舞いで担保。

### Q3: 問題が起きたときの責任は？
A: 振る舞いテストとモニタリングで早期発見。リスクベースでレビュー深度を調整。

### Q4: チームメンバーのスキルが育たないのでは？
A: 「コードを読む力」から「振る舞いを設計する力」「AIを使いこなす力」へのシフト。
